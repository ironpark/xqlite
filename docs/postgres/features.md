# PostgreSQL 호환: 지원 기능

xqlite PostgreSQL 방언이 지원하는 데이터 타입, SQL 문장, 연산자, 내장 함수 및 시스템 카탈로그의 상세 명세입니다.

---

## 1. 데이터 타입 및 리터럴

테이블은 SQLite의 `STRICT` 모드로 생성되며, PostgreSQL의 타입 제약과 검사 규칙을 준수합니다.

| 카테고리 | PostgreSQL 타입 | 저장 방식 | 설명 및 제약 |
| --- | --- | --- | --- |
| **정수** | `smallint` (int2)<br>`integer` / `int` (int4)<br>`bigint` (int8) | `INTEGER` | 각각 16비트(-32,768 ~ 32,767), 32비트(-2³¹ ~ 2³¹-1), 64비트 범위를 엄격히 검사합니다. 범위를 벗어나면 `22003: integer out of range` 오류가 발생합니다. |
| **일련번호** | `smallserial`<br>`serial`<br>`bigserial` | `INTEGER` | 자동으로 `GENERATED BY DEFAULT AS IDENTITY` 시퀀스가 바인딩된 정수 열로 생성됩니다. |
| **부동소수점** | `real` (float4)<br>`double precision` (float8) | `REAL` | IEEE 754 단정밀도 및 배정밀도 부동소수점입니다. 문자열은 `float8in()`·`float4in()`처럼 읽고(`'Infinity'`, `'-inf'`, `'abc'`는 오류), `real`은 캐스트와 저장에서 단정밀도로 반올림합니다(`1.1::real::float8`은 `1.100000023841858`, 범위 밖은 `value out of range: overflow`/`underflow`). 텍스트는 `float8out()`·`float4out()`의 것입니다(`1e10::float8::text`는 `10000000000`, `1e6::real`은 `1e+06`). `-(0.0::float8)`은 `-0`입니다. NaN은 지원하지 않습니다([차이점](differences.md)). 정수·실수와 비교한 문자열 상수는 그 타입으로 읽습니다(`10 > '7'`은 참). |
| **임의 정밀도** | `numeric[(p, s)]`<br>`decimal[(p, s)]` | `REAL` 또는 내부 인코딩 | 최대 정밀도와 스케일을 지원하며 정확한 사칙연산과 반올림을 수행합니다. |
| **불리언** | `boolean` / `bool` | `INTEGER` (0 또는 1) | 리터럴 `true`/`false`, `'t'`/`'f'`, `'yes'`/`'no'`, `'1'`/`'0'`을 지원합니다. 텍스트로 바꾸면 PostgreSQL과 같습니다: 캐스트(`b::text`, `b::varchar(n)`), `\|\|`, `text` 열에 저장은 `true`/`false`(`xq_pg_bool_text()`), `concat()`·`concat_ws()`·`format()`은 출력 함수의 `t`/`f`(`xq_pg_bool_out()`). |
| **문자열** | `text`<br>`varchar(n)` / `character varying(n)`<br>`char(n)` / `character(n)` | `TEXT` | `varchar(n)`은 최대 길이 n을 검사하며, `char(n)`은 후행 공백 패딩 규칙을 따릅니다. |
| **날짜 및 시간** | `date`<br>`time [without time zone]`<br>`timetz` / `time with time zone`<br>`timestamp [without time zone]`<br>`timestamptz` / `timestamp with time zone` | `TEXT` | ISO-8601 및 PostgreSQL 표준 형식 문자열로 저장됩니다. `now()`, `CURRENT_TIMESTAMP`, `clock_timestamp()`를 지원합니다. |
| **시간 간격** | `interval [fields]` | 내부 인코딩 | 월(months), 일(days), 마이크로초(microseconds)로 구성된 정밀 간격을 지원합니다. |
| **고유 식별자** | `uuid` | 16바이트 `BLOB` | 표준 36자 하이픈 형식 텍스트와 16바이트 BLOB 간 자동 변환됩니다. `gen_random_uuid()` (v4) 및 `uuidv7()`을 지원합니다. |
| **JSON** | `json`<br>`jsonb` | 정규화 텍스트 / `jsonb` 바이너리 | `json`은 텍스트 보존형, `jsonb`는 공백 제거 및 키 정렬이 적용된 바이너리/정규화 표현입니다. |
| **배열** | `T[]` (예: `int[]`, `text[]`, `numeric[]` 등) | `TEXT` | 다차원 배열, 슬라이스, 리터럴(`'{1, 2, 3}'` 또는 `ARRAY[1, 2, 3]`)을 지원합니다. |
| **네트워크 주소** | `inet`<br>`cidr` | `TEXT` | PostgreSQL이 쓰는 텍스트로 저장합니다(`'192.168.1.5'`, `'10.1.2.3/8'`, IPv6는 RFC 5952의 줄인 꼴 `'2001:db8::1'`). 입력은 캐스트와 저장할 때 읽고, 잘못된 값은 `22P02: invalid input syntax for type inet`입니다. `cidr`은 길이 오른쪽에 비트가 있으면 오류입니다. 비교와 정렬은 텍스트 순서입니다. |
| **열거형** | `CREATE TYPE name AS ENUM (...)` | `TEXT` | 레이블의 텍스트로 저장하고, 열마다 레이블 중 하나인지 보는 CHECK(`invalid input value for enum name`, `22P02`)를 둡니다. 비교와 정렬은 레이블의 순서가 아니라 텍스트 순서입니다. |
| **기타 / 카탈로그** | `bytea`<br>`oid`, `name`, `regtype`, `regclass` | `BLOB` / `INTEGER` / `TEXT` | 시스템 카탈로그 및 드라이버 연동에 필요한 특수 타입을 지원합니다. |

## 2. 지원 SQL 문장

### 2.1 DDL (데이터 정의어)

- **`CREATE TABLE`**
  - 열 제약: `PRIMARY KEY`, `UNIQUE`, `NOT NULL`, `CHECK (expr)`, `DEFAULT expr`
  - 외래 키: `REFERENCES tbl(col) [ON DELETE {CASCADE | SET NULL | RESTRICT}]`
  - 정체성 열: `GENERATED {ALWAYS | BY DEFAULT} AS IDENTITY [(options)]`
  - 생성 열: `GENERATED ALWAYS AS (expr) STORED`
  - `IF NOT EXISTS`, `TEMPORARY` / `TEMP` 테이블 지원
- **`ALTER TABLE`**
  - `ADD COLUMN [IF NOT EXISTS]`, `DROP COLUMN [IF EXISTS]`
  - `RENAME COLUMN old TO new`, `RENAME TO new_table`
  - `ALTER [COLUMN] c SET DEFAULT expr / DROP DEFAULT`: 행은 값을 그대로 가집니다(ADD COLUMN 전의 행도).
  - `ALTER [COLUMN] c SET NOT NULL / DROP NOT NULL`: NULL인 행이 있으면 `column "c" of relation "t" contains null values`(23502). 기본 키 열은 `DROP NOT NULL`할 수 없습니다(42P16).
  - `ALTER [COLUMN] c [SET DATA] TYPE type [COLLATE c] [USING expr]`: 저장 타입과 타입의 CHECK를 바꾸고 값을 `USING`(없으면 열 자신)의 캐스트로 다시 씁니다. 정수 기본 키(rowid) 열을 INTEGER 아닌 타입으로 바꾸는 것은 지원하지 않습니다.
  - `ADD [CONSTRAINT name] CHECK (expr) | FOREIGN KEY (...) REFERENCES ... | UNIQUE (...)`: 있는 행을 먼저 검사합니다(`check constraint ... is violated by some row`, 외래 키 위반). 이름이 없으면 PostgreSQL의 이름(`t_a_check`, `t_a_fkey`, `t_a_key`, 겹치면 `t_a_check1` ...). `UNIQUE`는 그 이름의 고유 인덱스입니다. `ADD PRIMARY KEY`는 지원하지 않습니다.
  - `DROP CONSTRAINT [IF EXISTS] name`: CHECK, 외래 키, UNIQUE(그 인덱스)
  - 한 문장에 여러 동작(`ADD COLUMN a int, ADD COLUMN b text, ALTER COLUMN c SET NOT NULL`): 동작마다 앞의 것이 바꾼 테이블에서 차례로 돌고, 하나가 실패하면 모두 되돌립니다.
  - 상수가 아닌 DEFAULT의 `ADD COLUMN`(`DEFAULT now()`): 있는 행은 그 값을 받습니다(SQLite의 ADD COLUMN은 받지 않음).
- 문자열 상수의 `DEFAULT`는 테이블을 만들 때 열의 타입으로 읽습니다(`bool DEFAULT 'f'`는 false, `int DEFAULT '0'`, 날짜, `inet`, 열거형). 읽을 수 없으면 그 타입의 입력 오류입니다.
- **`CREATE TYPE name AS ENUM ('a', ...)`**, **`ALTER TYPE name ADD VALUE [IF NOT EXISTS] 'v' [BEFORE | AFTER 'w']`**, **`ALTER TYPE name RENAME VALUE 'a' TO 'b'`**(행의 값도 바뀜), **`DROP TYPE [IF EXISTS] name`**(그 타입의 열이 있으면 `2BP01`). 타입은 `public`에만 둡니다. 복합 타입·범위 타입은 지원하지 않습니다.
- **`DROP EXTENSION [IF EXISTS] name`**: 설치된 확장이 없으므로 `IF EXISTS`면 NOTICE만 냅니다.
- **`CREATE INDEX`**
  - 일반 인덱스 및 고유 인덱스 (`UNIQUE`)
  - 식 인덱스 (`CREATE INDEX ON tbl (lower(email))`)
  - 부분 인덱스 (`WHERE active = true`)
  - `IF NOT EXISTS` 지원
- **`CREATE VIEW`** / **`DROP VIEW`**: `CREATE OR REPLACE VIEW`, `IF EXISTS`
- **`CREATE SCHEMA`** / **`DROP SCHEMA`**: 네임스페이스 격리 및 `CASCADE` 지원
- **`CREATE SEQUENCE`** / **`ALTER SEQUENCE`**: `INCREMENT`, `MINVALUE`, `MAXVALUE`, `START`, `CYCLE`
- **`TRUNCATE TABLE [tbl, ...]`**: 테이블 고속 비우기

### 2.2 DML (데이터 조작어)

- **`SELECT`**
  - `DISTINCT [ON (expr, ...)]`: `DISTINCT ON`은 `ORDER BY` 순서로 묶음마다 첫 행을 남깁니다. `ORDER BY`가 `DISTINCT ON`의 식으로 시작하지 않으면 PostgreSQL처럼 `SELECT DISTINCT ON expressions must match initial ORDER BY expressions`(42P10)입니다.
  - `FROM` 절: 테이블 조인(`INNER`, `LEFT`, `RIGHT`, `FULL OUTER`, `CROSS`), 서브쿼리, 테이블 값 함수(`unnest`, `generate_series`, `jsonb_to_recordset`), `JOIN ... USING (cols) AS alias`(`alias.col`이 합친 열)
  - `LATERAL` 서브쿼리: `FROM t, LATERAL (...)`, `[CROSS | LEFT] JOIN LATERAL (...) ON ...`. 앞 항목의 열을 쓰는 서브쿼리는 앞 항목의 행마다 다시 돕니다(그룹마다 상위 N개 같은 질의). `FROM`의 함수도 앞 항목의 열을 인자로 받습니다(`generate_series(1, t.n)`, `unnest(t.arr)`). 뷰에도 쓸 수 있습니다(`LEFT JOIN LATERAL ... ON` 포함): SQLite 텍스트로는 `json_each()`와 엔진 함수 `xq_lateral_rows()`·`xq_lateral_col()`로 저장되어 확장을 올린 sqlite3도 읽습니다([차이점](differences.md)).
  - `RIGHT`/`FULL JOIN LATERAL (...)`(과 `RIGHT`/`FULL JOIN`의 함수)은 앞 항목을 쓰지 않으면 보통 조인입니다. 그 조인의 왼쪽 항목을 쓰면 PostgreSQL처럼 `42P10: invalid reference to FROM-clause entry for table "t"`(DETAIL `The combining JOIN type must be INNER or LEFT for a LATERAL reference.`)이고, 위치는 그 열입니다.
  - `WHERE`, `GROUP BY`, `HAVING`
  - `GROUP BY [ALL | DISTINCT]`의 `ROLLUP (...)`, `CUBE (...)`, `GROUPING SETS (...)`, `()`와 보통 식을 섞은 것(집합들의 곱), `GROUPING(expr, ...)`. 다른 집합의 열은 NULL이고, 집계의 `DISTINCT`·`FILTER`·`ORDER BY`, `HAVING`, 전체에 대한 `ORDER BY`·`LIMIT`가 PostgreSQL처럼 동작합니다. 윈도우 함수(집계를 인자나 `OVER`에 쓰는 `sum(sum(x)) OVER (...)`, `rank() OVER (ORDER BY count(*))`, `PARTITION BY grouping(...)`), `DISTINCT ON`, `FETCH ... WITH TIES`와 함께 쓸 수 있습니다. 이때는 집합마다의 `UNION ALL`을 파생 테이블로 두고 그 위에서 윈도우 함수와 `DISTINCT ON`, `ORDER BY`를 계산합니다.
  - 윈도우 함수 (`OVER (PARTITION BY ... ORDER BY ... [frame])`)
  - 집합 연산: `UNION [ALL]`, `INTERSECT [ALL]`, `EXCEPT [ALL]` (`ALL`은 중복을 센 다중 집합 연산)
  - 정렬 및 페이징: `ORDER BY ... [ASC | DESC] [NULLS FIRST | NULLS LAST]`, `LIMIT n OFFSET m`, `FETCH FIRST n ROWS ONLY`, `FETCH FIRST n ROWS WITH TIES`(`ORDER BY`가 없으면 42601)
  - 공통 테이블 식: `WITH [RECURSIVE] name AS (...)`
- **`INSERT`**
  - 다중 행 삽입: `VALUES (...), (...)`
  - 충돌 처리: `ON CONFLICT (col, ...) DO NOTHING` 또는 `ON CONFLICT (col) DO UPDATE SET col = EXCLUDED.col [WHERE ...]`
  - `ON CONFLICT ON CONSTRAINT name`: 그 이름의 PRIMARY KEY·UNIQUE 제약(`pg_constraint`의 이름: `t_pkey`, `t_a_key`, `CONSTRAINT name`)의 열. 제약이 아닌 고유 인덱스(`CREATE UNIQUE INDEX`)나 없는 이름은 PostgreSQL처럼 `constraint "x" for table "t" does not exist`(42704)
  - `OVERRIDING SYSTEM VALUE`, `OVERRIDING USER VALUE`(identity 열에 준 값은 버리고 그 열의 기본값: `VALUES`의 값은 `DEFAULT`로, 질의의 그 열은 빼고)
  - 결과 반환: `RETURNING expr, ...`
- **`UPDATE`**
  - 조인 업데이트: `UPDATE tbl SET ... FROM other_tbl WHERE ...`(`text` 열에 문자열 값도)
  - 여러 열: `SET (a, b) = (1, 2)`, `SET (a, b) = (SELECT ...)`
  - 없는 열에 쓰면 `column "zz" of relation "t" does not exist`(42703)
  - 결과 반환: `RETURNING expr, ...`
- **`DELETE`**
  - 조인 삭제: `DELETE FROM tbl USING other_tbl WHERE ...`
  - 결과 반환: `RETURNING expr, ...`
- **`RETURNING`의 `OLD`·`NEW`**(PostgreSQL 18): `INSERT`·`UPDATE`·`DELETE`·`MERGE`의 `RETURNING old.a, new.a, old.*, new.*`, 이름을 바꾸는 `RETURNING WITH (OLD AS o, NEW AS n) o.a, n.a`. 바꾸기 전과 뒤의 행이고, 없는 쪽(`INSERT`의 old, `DELETE`의 new)은 NULL입니다. `ON CONFLICT DO UPDATE`의 old는 있던 행입니다. 행 전체(`RETURNING new`)는 지원하지 않습니다.
- **`MERGE`**(PostgreSQL 15–18)
  - `[WITH ...] MERGE INTO target [AS t] USING source [AS s] ON cond`: 원본은 테이블, 서브쿼리, `VALUES`
  - `WHEN MATCHED [AND cond] THEN UPDATE SET ... | DELETE | DO NOTHING`
  - `WHEN NOT MATCHED [BY TARGET] [AND cond] THEN INSERT [(cols)] [OVERRIDING ...] VALUES (...) | INSERT DEFAULT VALUES | DO NOTHING`
  - `WHEN NOT MATCHED BY SOURCE [AND cond] THEN UPDATE | DELETE | DO NOTHING`(PostgreSQL 17)
  - 원본·대상 행의 짝마다 조건이 맞는 첫 `WHEN` 절. 한 대상 행을 두 원본 행이 바꾸려 하면 `MERGE command cannot affect row a second time`(21000)
  - `RETURNING`(PostgreSQL 17): `merge_action()`, 대상과 원본의 열(`*`은 원본의 열 다음 대상의 열), `OLD`·`NEW`. 행은 조인을 읽은 순서입니다
  - 제약, 기본값, identity, 생성 열, 열 타입의 저장 변환은 `INSERT`·`UPDATE`의 것 그대로입니다. 바뀐 행 수가 명령 태그(`MERGE n`)입니다
  - `WITH m AS (MERGE ... RETURNING ...) SELECT ...`
  - `WHEN` 절이 볼 수 없는 쪽을 쓰면 `invalid reference to FROM-clause entry for table "s"`(42P01), `merge_action()`을 `RETURNING` 밖에서 쓰면 42601
  - 뷰가 대상(PostgreSQL 17): 자동으로 갱신할 수 있는 뷰(테이블 하나를 읽고 `DISTINCT`, `GROUP BY`, `HAVING`, 집합 연산, `WITH`, `LIMIT`/`OFFSET`, 집계, 윈도우 함수가 없는 뷰)는 그 테이블에 씁니다. 뷰의 `WHERE`가 빼는 행은 대상이 아니고, 테이블의 열인 뷰의 열(이름을 바꾼 것도)만 쓸 수 있으며 계산한 열은 읽기만 합니다. `RETURNING`(`merge_action()` 포함)은 뷰의 열입니다. 뷰에서의 `UPDATE SET col = DEFAULT`는 PostgreSQL처럼 NULL(뷰의 열에는 기본값이 없음), `INSERT`가 빠뜨린 열은 테이블의 기본값입니다.
    - 갱신할 수 없는 뷰는 PostgreSQL의 오류: `cannot update view "v"`(55000, DETAIL 그 이유, HINT `INSTEAD OF` 트리거), 테이블의 열이 아닌 열에 쓰면 `cannot merge into column "c" of view "v"`(0A000), 뷰에 없는 열은 42703. `DO NOTHING`만 있으면 갱신할 수 없는 뷰도 됩니다.
    - 지원하지 않음(0A000): 뷰의 뷰, `INSTEAD OF` 트리거의 뷰(PostgreSQL 방언에는 트리거가 없음), `WITH CHECK OPTION`(뷰를 만들 수 없음), 뷰가 대상일 때의 `RETURNING`의 `OLD`/`NEW`, 뷰의 열에 `SET (a, b) = (SELECT ...)`·`SET arr[i] = ...`. 뷰에 대한 `INSERT`·`UPDATE`·`DELETE`는 여전히 지원하지 않습니다.
  - `EXPLAIN MERGE ...`: 단계마다(조인, `WHEN` 절의 동작, 뷰의 `UPDATE`가 새 값을 계산하는 단계) 그 문장의 계획을 단계 이름의 줄 아래에 보이고, `RETURNING`의 질의 계획이 뒤에 옵니다. 데이터 변경 `WITH`의 `EXPLAIN`도 하위 문장마다(`WITH d: DELETE`) 그렇게 보입니다. 단계는 실행되지 않습니다. 형식은 PostgreSQL의 것과 다릅니다.
- **데이터 변경 `WITH`**: `WITH d AS (DELETE ... RETURNING *) INSERT INTO log SELECT * FROM d`, `WITH u AS (UPDATE ... RETURNING ...) SELECT ...`, `INSERT`·`UPDATE`·`DELETE`·`MERGE`를 여럿, 다른 `WITH` 질의와 섞어서. 읽지 않아도 돕니다. `RETURNING`이 없는 것을 읽으면 `WITH query "d" does not have a RETURNING clause`(0A000), 최상위가 아닌 `WITH`에 있으면 0A000입니다. 명령 태그는 바깥 문장의 것입니다(`INSERT 0 n`). 스냅숏의 차이는 [차이점](differences.md#1-엔진-설계-및-동작-차이점)에 있습니다.

### 2.3 커서

- **`DECLARE name [ASENSITIVE | INSENSITIVE] [[NO] SCROLL] CURSOR [{WITH | WITHOUT} HOLD] FOR query`**: `query`는 `SELECT`, `VALUES`, `TABLE`, `WITH ... SELECT`, 괄호의 질의이고, `$1` 같은 매개변수를 쓸 수 있습니다(드라이버가 서버에서 바인딩하는 psycopg 3의 서버 쪽 커서).
  - `DECLARE`가 실행될 때 질의를 끝까지 돌려 행을 세션의 메모리에 둡니다(`src/dialect/postgres/cursor.zig`). 그래서 커서는 언제나 insensitive입니다(뒤의 `INSERT`·`UPDATE`가 보이지 않음, PostgreSQL이 허용하는 동작이고 holdable 커서는 PostgreSQL도 같음). 열의 이름과 타입은 질의의 것입니다(`boolean`의 `t`/`f`, `numeric(6,2)`의 자릿수, `RowDescription`의 OID).
  - `HOLD`가 없으면 트랜잭션 블록 안에서만 선언할 수 있고(`25P01: DECLARE CURSOR can only be used in transaction blocks`; 와이어 서버의 여러 문장 질의가 여는 암묵적 트랜잭션도 블록입니다), 트랜잭션이 끝나면(`COMMIT`, `ROLLBACK`) 닫힙니다. `WITH HOLD`는 `COMMIT` 뒤에도 그 자리에 남고, 선언한 트랜잭션이 롤백되면 없어집니다. `ROLLBACK TO SAVEPOINT`는 그 세이브포인트 뒤에 선언한 커서를 닫습니다. 위치는 트랜잭션을 따라 되돌아가지 않습니다(PostgreSQL과 같음).
  - 오류: 같은 이름(`42P03`), `SCROLL`과 `NO SCROLL`·`ASENSITIVE`와 `INSENSITIVE`를 함께(`42P11`), `FOR UPDATE`/`FOR SHARE`와 `WITH HOLD`·`SCROLL`(`0A000`)·`INSENSITIVE`(`42P11`), 질의의 오류는 그 자리에서.
- **`FETCH [direction] [FROM | IN] name`**, **`MOVE [direction] [FROM | IN] name`**: `NEXT`, `PRIOR`, `FIRST`, `LAST`, `ABSOLUTE n`, `RELATIVE n`, `n`, `ALL`, `FORWARD [n | ALL]`, `BACKWARD [n | ALL]`. 첫 행 앞, 행 위, 마지막 행 뒤의 위치와 행 수는 PostgreSQL의 `DoPortalRunFetch()`·`PortalRunSelect()`를 그대로 따릅니다(`FETCH 0`, `MOVE BACKWARD ALL`, 음수 개수 ...). `FETCH`는 준비해 두고 여러 번 실행해도 실행할 때마다 커서를 움직입니다. `MOVE`는 행을 내지 않고, 지나간 행 수가 문장의 `changes()`입니다(와이어 서버의 `MOVE n`).
  - 없는 커서는 `34000: cursor "x" does not exist`, `NO SCROLL` 커서를 뒤로 움직이면 `55000: cursor can only scan forward`(HINT도 같음).
  - `SCROLL`도 `NO SCROLL`도 없으면 PostgreSQL처럼 계획이 뒤로 갈 수 있을 때만 뒤로 갑니다. xqlite는 계획 대신 질의의 꼴로 정합니다: 집계, 윈도우, 조인, 집합 연산, `FROM` 없는 질의, 한 행의 `VALUES`, `FOR UPDATE`는 뒤로 가지 못하고, `GROUP BY`·`DISTINCT`·`IN (SELECT ...)`는 `ORDER BY`가 있을 때만 갑니다. `pg_cursors.is_scrollable`도 이것입니다.
- **`DECLARE name BINARY CURSOR ...`**: 와이어 서버의 단순 질의로 `FETCH`하면 PostgreSQL처럼 행을 이진 형식으로 보냅니다(`RowDescription`의 형식 코드 1). 와이어 서버가 이진 형식을 모르는 타입(`date`, `timestamp` ...)의 열은 텍스트(형식 코드 0)입니다. 확장 질의의 `FETCH`는 `Bind`의 결과 형식을 따르고, 내장 API의 결과는 그대로입니다. `pg_cursors.is_binary`가 참입니다.
- **`CLOSE name`**, **`CLOSE ALL`**.
- **`UPDATE ... WHERE CURRENT OF name`**, **`DELETE ... WHERE CURRENT OF name`**: 커서가 테이블 하나를 그대로 훑는 질의일 때(조인, 집계, `DISTINCT`, 집합 연산이 없고, `ORDER BY`는 `FOR UPDATE`/`FOR SHARE`와 함께일 때만: PostgreSQL의 "simply updatable scan") 커서가 선 행입니다. `DECLARE`가 행마다 `rowid`를 함께 기억합니다. 그렇지 않으면 `24000: cursor "c" is not a simply updatable scan of table "t"`, 행 위에 있지 않으면 `24000: cursor "c" is not positioned on a row`.
- **`pg_cursors`** 뷰: `name`, `statement`, `is_holdable`, `is_binary`, `is_scrollable`, `creation_time`.
- psql의 `\set FETCH_COUNT n`(psql 17부터는 커서 대신 libpq의 chunked 모드), psycopg2의 이름 있는 커서(`DECLARE ... WITHOUT HOLD`, `scrollable`, `withhold`), psycopg 3의 서버 쪽 커서(매개변수, 포털 `Describe`)가 와이어 서버에서 동작합니다.

### 2.4 트랜잭션과 세션

- **`COMMIT AND CHAIN`**, **`ROLLBACK AND CHAIN`**: 끝낸 자리에서 새 트랜잭션을 엽니다(`OP_AutoCommit`의 P3, PostgreSQL 방언만 씀). 트랜잭션 밖이면 `25P01: COMMIT AND CHAIN can only be used in transaction blocks`. `AND NO CHAIN`은 그냥 끝냅니다.
- **`SET LOCAL name {TO | =} value`**, `set_config(name, value, true)`: 트랜잭션이 끝날 때까지만입니다. 트랜잭션 밖의 `SET LOCAL`은 아무것도 하지 않고 `WARNING: SET LOCAL can only be used in transaction blocks`입니다. `SET`도 PostgreSQL처럼 트랜잭션을 따릅니다: 롤백되면 트랜잭션 전의 값으로 돌아가고, 커밋되면 마지막 `SET`의 값이 남습니다(그 뒤의 `SET LOCAL`은 남지 않음). `RESET ALL`도 같습니다. 세이브포인트로 되돌리는 것은 설정을 되돌리지 않습니다.
- **`PREPARE name [(type, ...)] AS statement`**, **`EXECUTE name [(arg, ...)]`**, **`DEALLOCATE [PREPARE] {name | ALL}`**: 문장의 텍스트를 세션에 두고(`src/dialect/postgres/commands.zig`), `EXECUTE`가 `$n`을 인자(`PREPARE`가 타입을 주었으면 그 타입으로 캐스트)로 바꾼 문장을 컴파일합니다. 계획을 한 번 세워 두지는 않으므로 `EXECUTE`마다 컴파일합니다. 오류: 같은 이름(`42P05`), 없는 이름(`26000`), 인자 수(`42601`, DETAIL `Expected 1 parameters but got 0.`; 매개변수가 없는 문장은 인자를 무시함). 와이어 서버의 태그는 실행한 문장의 것입니다(`INSERT 0 1`, `SELECT 2`).
- **`DISCARD ALL | PLANS | SEQUENCES | TEMP`**: `ALL`은 커서를 닫고 준비된 문장을 지우고 `RESET ALL`과 아래 셋을 합니다(트랜잭션 블록 안이면 `25001`). `PLANS`는 컴파일된 문장을 만료시키고, `SEQUENCES`는 `currval()`·`lastval()`을 잊고, `TEMP`는 임시 테이블과 뷰를 지웁니다.
- **`SET CONSTRAINTS {ALL | [schema.]name, ...} {DEFERRED | IMMEDIATE}`**: `DEFERRABLE`인 외래 키마다 트랜잭션이 끝날 때까지 미루거나 바로 검사하게 합니다(`src/dialect/postgres/setconstraints.zig`). SQLite는 외래 키의 위반을 미룰지를 문장을 컴파일할 때 정하므로, PostgreSQL 방언으로 컴파일할 때 연결이 가진 모드(`ALL`의 모드와 그 뒤에 이름으로 준 모드, 이름이 앞섬)를 따르고, 모드가 바뀌거나 트랜잭션이 끝나면 컴파일된 문장을 만료시킵니다. SQLite 방언의 프로그램은 바뀌지 않습니다.
  - `DEFERRABLE [INITIALLY IMMEDIATE]`도 이제 스키마 텍스트에 남습니다(`REFERENCES ... DEFERRABLE`, `pg_constraint.condeferrable`). 이 변경 전에 만든 테이블의 `DEFERRABLE INITIALLY IMMEDIATE`는 남아 있지 않아 `DEFERRABLE`이 아닌 것으로 봅니다.
  - 이름은 PostgreSQL처럼 찾습니다: 스키마가 있으면 그 스키마에서, 없으면 `pg_temp`와 `search_path`의 스키마 중 그 이름의 제약이 있는 첫 스키마에서. 없는 이름은 `42704`, 없는 스키마는 `3F000`, `DEFERRABLE`이 아닌 제약(외래 키, 키, CHECK, NOT NULL)을 `DEFERRED`로 주면 `55000: constraint "x" is not deferrable`입니다(`IMMEDIATE`는 그냥 넘어감). `ALL`은 `DEFERRABLE`인 외래 키만 바꿉니다.
  - `IMMEDIATE`는 바로 검사로 바뀌는 외래 키의 미뤄 둔 위반을 그 자리에서 검사합니다(`23503`, DETAIL `Key (x)=(5) is not present in table "p".`). 연결은 미룬 위반을 외래 키별로 세지 않고 하나의 수로만 세므로, 그 수가 0이 아니면 해당 외래 키를 `PRAGMA foreign_key_check`처럼 테이블 전체에서 찾습니다. 오류 뒤에는 모드가 바뀌지 않습니다.
  - 세이브포인트를 따릅니다: `ROLLBACK TO`는 그 세이브포인트를 만들 때의 모드로 돌아가고, `RELEASE`는 바꾼 모드를 남깁니다.
  - 트랜잭션 블록 밖이면 이름을 검사한 뒤 `WARNING: SET CONSTRAINTS can only be used in transaction blocks`만 내고 아무것도 바꾸지 않습니다. 블록 안인지는 실행할 때 보므로 와이어 서버의 여러 문장 질의가 여는 암묵적 블록에서도 모드를 바꿉니다. 다만 경고는 컴파일할 때 정하므로, 그때 트랜잭션 밖이었으면 암묵적 블록 안이라도 경고가 함께 나갑니다(PostgreSQL은 내지 않음).
  - 모드가 그대로이면 컴파일된 문장을 만료시키지 않습니다.
- **`LOCK [TABLE] [ONLY] name [*], ... [IN mode MODE] [NOWAIT]`**: 트랜잭션 블록(와이어 서버의 여러 문장 질의가 여는 암묵적 블록도) 안에서(`25P01`, 실행할 때 검사) 테이블이 든 데이터베이스(파일)의 SQLite 잠금을 그 자리에서 잡습니다. 없는 테이블은 `42P01`입니다.
  - `ROW EXCLUSIVE`, `SHARE UPDATE EXCLUSIVE`, `SHARE ROW EXCLUSIVE`, `EXCLUSIVE`, `ACCESS EXCLUSIVE`(기본)는 쓰기 잠금(`RESERVED`)입니다. 미뤄 둔 트랜잭션이 `BEGIN IMMEDIATE`처럼 바뀝니다.
  - `ACCESS SHARE`, `ROW SHARE`, `SHARE`는 읽기 트랜잭션(`SHARED`)을 엽니다. 스냅숏이 그때 정해지고, 롤백 저널 모드에서는 끝날 때까지 다른 연결이 커밋하지 못합니다.
  - 다른 연결이 잠금을 쥐고 있으면 바쁨 처리기(`busy_timeout`)만큼 기다리고, 그래도 안 되면 `55P03: canceling statement due to lock timeout`입니다. `NOWAIT`는 기다리지 않고 `55P03: could not obtain lock on relation "t"`입니다.
  - 잠금은 테이블이 아니라 파일 전체에 걸립니다([차이점](differences.md)).

## 3. 연산자 및 표현식

### 3.1 논리, 비교 및 산술 연산자
- 논리: `AND`, `OR`, `NOT`, `IS [NOT] TRUE/FALSE/NULL`
- 비교: `=`, `<>`, `!=`, `<`, `<=`, `>`, `>=`, `IS [NOT] DISTINCT FROM`, `[NOT] BETWEEN [SYMMETRIC | ASYMMETRIC]`
- 행: `ROW(a, b) IS [NOT] NULL`(모든 필드가 NULL / 어느 필드도 NULL이 아님), `(start, end) OVERLAPS (start, end)`(날짜·타임스탬프, 끝 대신 `interval` 상수도, NULL과 거꾸로 된 끝은 PostgreSQL의 규칙대로)
- 패턴 매칭:
  - `LIKE`, `ILIKE` (대소문자 무시), `NOT LIKE`, `NOT ILIKE`
  - 정규식: `~` (일치), `~*` (대소문자 무시 일치), `!~`, `!~*`
  - `SIMILAR TO`
- 타입 캐스트: `expr::type` 및 `CAST(expr AS type)`
- 불리언과 만난 문자열 상수는 PostgreSQL처럼 불리언으로 읽습니다: 비교(`b = 'yes'`), `IN`, `CASE`, `BETWEEN`, `coalesce`, `nullif`, `greatest`, `least`, `ARRAY[...]`, `VALUES`의 열, `UNION`/`INTERSECT`/`EXCEPT`의 열(왼쪽부터 두 항씩). 불리언이 아니면 문장을 컴파일할 때 실패합니다(`invalid input syntax for type boolean: "x"`, 뷰와 CHECK도). `INSERT ... VALUES`의 행은 각자 그 열의 타입으로 저장됩니다.
- CASE 식: `CASE WHEN ... THEN ... ELSE ... END`

### 3.2 배열 연산자
- 원소 포함 검사: `val = ANY(arr)`, `val <> ALL(arr)`, `val LIKE ANY(arr)`
- 포함 관계: `arr1 @> arr2` (포함), `arr1 <@ arr2` (포함됨), `arr1 && arr2` (오버랩)
- 배열 연결: `arr1 || arr2`, `val || arr`, `arr || val`
- 첨자 접근: `arr[i]`, 다차원 `arr[i][j]`, 슬라이스 `arr[lo:hi]` (1-based 인덱스)

### 3.3 JSON / JSONB 연산자
- 필드 추출:
  - `json -> 'key'` (JSON 반환), `json ->> 'key'` (텍스트 반환)
  - `json -> idx` (배열 인덱스 반환), `json ->> idx` (배열 인덱스 텍스트 반환)
  - `json #> '{a,b}'` (경로 탐색 JSON), `json #>> '{a,b}'` (경로 탐색 텍스트)
- 존재 확인 및 포함:
  - `jsonb ? 'key'` (키 존재 여부)
  - `jsonb ?| array['a', 'b']` (키 중 하나라도 존재)
  - `jsonb ?& array['a', 'b']` (키 모두 존재)
  - `jsonb1 @> jsonb2` (JSONB 포함 검사)
- 삭제 연산: `jsonb - 'key'`, `jsonb - idx`, `jsonb #- '{a,b}'`

## 4. 내장 함수 및 시스템 카탈로그

### 4.1 주요 내장 함수
- **문자열 함수**: `length`, `octet_length`, `lower`, `upper`, `substr` / `substring`, `trim`, `btrim`, `ltrim`, `rtrim`, `concat`, `concat_ws`, `format`, `split_part`, `replace`, `repeat`, `reverse`, `left`, `right`, `lpad`, `rpad`, `md5`
- **바이너리 함수**: `sha224`, `sha256`, `sha384`, `sha512`(bytea), `encode(bytea, 'hex' | 'base64' | 'escape')`, `decode(text, format)`. 식 인덱스(`ON t (sha256(url::bytea))`)는 그 식의 `ON CONFLICT` 대상, `WHERE`, `ORDER BY`에서 쓰입니다(방언 함수는 세션의 문장에서도 스키마가 부르는 한정 이름 `xq_postgres_sha256`으로 내려갑니다).
- **`pg_typeof()`**: 문장을 컴파일할 때 식의 타입을 알면 그 타입의 이름입니다(`bigint`, `smallint`, `character varying`, `integer[]`, 열거형의 이름, 집계 `count(*)`의 `bigint`; `xq_pg_typeof_as(x, 'bigint')`). 모르면 값의 저장 형태로 정합니다(정수는 32비트 범위면 `integer`).
- **네트워크 주소 함수**: `host(inet)`, `masklen(inet)`, `family(inet)`
- **수학 함수**: `abs`, `ceil`, `floor`, `round`, `trunc`, `power`, `sqrt`, `exp`, `ln`, `log`, `mod`, `sign`, `greatest`, `least`
  - 배정밀도: `sin`, `cos`, `tan`, `cot`, `asin`, `acos`, `atan`, `atan2`, 도 단위의 `sind`, `cosd`, `tand`, `cotd`, `asind`, `acosd`, `atand`, `atan2d`(특수 각에서 정확: `sind(30)`은 `0.5`), `sinh`, `cosh`, `tanh`, `asinh`, `acosh`, `atanh`, `cbrt`, `degrees`, `radians`, `erf`, `erfc`, `gamma`, `lgamma`. 오류(`input is out of range`, `value out of range: overflow`/`underflow`, 22003)와 결과 타입도 PostgreSQL과 같습니다. `exp`·`log`·`pow` 계열은 musl의 구현을 옮긴 `src/dialect/libm.zig`로 계산해 어느 플랫폼에서도 PostgreSQL(musl)과 같은 자릿수입니다. `round(x)`는 배정밀도에서 짝수 쪽 반올림(`round(2.5::float8)`은 `2`)입니다.
  - 난수: `random()`, `random(min, max)`(정수, bigint, numeric), `random_normal([mean [, stddev]])`, `setseed(s)`. PostgreSQL의 PRNG(xoroshiro128**)를 세션마다 두므로 `setseed()` 뒤의 값이 PostgreSQL과 같습니다.
- **날짜 및 시간 함수**: `now()`, `current_date`, `current_time`, `current_timestamp`, `clock_timestamp()`, `date_part('field', dt)`, `date_trunc('field', dt)`, `extract(field FROM dt)`, `age(dt1, dt2)`
- **형식화 함수**: `to_char(val, fmt)`, `to_date(str, fmt)`, `to_timestamp(str, fmt)`, `to_number(str, fmt)`
- **배열 함수**: `array_length(arr, dim)`, `array_dims(arr)`, `cardinality(arr)`, `array_append(arr, val)`, `array_prepend(val, arr)`, `array_cat(a1, a2)`, `array_to_string(arr, sep)`, `string_to_array(str, sep)`, `unnest(arr)`
- **JSON / JSONB 함수**: `to_json`, `to_jsonb`, `json_build_object`, `jsonb_build_object`, `json_build_array`, `jsonb_build_array`, `json_extract_path`, `jsonb_extract_path`, `json_object_keys`, `jsonb_object_keys`, `jsonb_set`, `jsonb_insert`, `json_array_length`, `jsonb_array_length`, `jsonb_each`, `jsonb_each_text`
- **UUID 함수**: `gen_random_uuid()` (v4), `uuidv7([interval])` (RFC 9562 v7 시간순 UUID), `uuid_extract_version(uuid)`, `uuid_extract_timestamp(uuid)`
- **집계 및 윈도우**: `count`, `sum`, `avg`, `min`, `max`, `string_agg(expr, delimiter [ORDER BY ...])`, `array_agg(expr [ORDER BY ...])`, `json_agg`, `jsonb_agg`, `row_number()`, `rank()`, `dense_rank()`, `lead()`, `lag()`, `first_value()`, `last_value()`
  - 통계 집계: `variance`, `var_samp`, `var_pop`, `stddev`, `stddev_samp`, `stddev_pop`(정수·numeric은 numeric으로, PostgreSQL의 자릿수와 스케일 그대로: `decimal_sql.zig`의 `xq_dec_var_*`; 실수는 double precision으로 `float8_accum()`의 합: `stats.zig`의 `xq_float_*`), `corr`, `covar_pop`, `covar_samp`, `regr_avgx`, `regr_avgy`, `regr_count`, `regr_intercept`, `regr_r2`, `regr_slope`, `regr_sxx`, `regr_sxy`, `regr_syy`, `any_value`. 모두 `FILTER (WHERE ...)`와 윈도우 함수(`OVER`)로 쓸 수 있습니다. 시작이 움직이는 프레임은 PostgreSQL처럼 프레임을 처음부터 다시 계산합니다(역함수가 없는 집계: `window.zig`).
  - 순서 집합 집계 `WITHIN GROUP (ORDER BY ...)`: `percentile_cont(f)`, `percentile_disc(f)`(분수 하나 또는 분수의 배열 `float8[]`), `mode()`. 가상 집합 집계: `rank(args)`, `dense_rank(args)`, `percent_rank(args)`, `cume_dist(args)` `WITHIN GROUP (ORDER BY ...)`(정렬 방향과 `NULLS FIRST/LAST`). 집계의 `ORDER BY`가 정렬한 행을 `stats.zig`의 엔진 집계(`xq_percentile_cont(f, x ORDER BY x)`, `xq_hypo_rank(flags, h, x, x < h, x > h)` ...)가 받으므로 뷰에도 쓸 수 있습니다. `OVER`와 함께 쓰면 PostgreSQL처럼 오류입니다.

### 4.2 시스템 카탈로그 및 뷰
PostgreSQL의 표준 카탈로그 구조를 가상 테이블로 노출합니다.
- `pg_catalog.pg_class`, `pg_attribute`, `pg_type`, `pg_namespace`, `pg_index`, `pg_constraint`, `pg_database`, `pg_tablespace`, `pg_am`, `pg_sequence`, `pg_cursors`(세션의 커서)
- `information_schema.tables`, `columns`, `schemata`, `views`, `table_constraints`, `key_column_usage`, `referential_constraints`
- `pg_type`은 PostgreSQL 18의 행을 모두 가집니다. xqlite가 만드는 타입(내장 타입, `information_schema`의 도메인, 있는 시스템 관계의 행 타입) 밖의 것(기하·텍스트 검색·범위 타입, xqlite에 없는 시스템 관계와 `information_schema` 뷰의 행 타입, 그 배열)은 `tools/dialect/pg-systypes.sql`이 PostgreSQL 18에서 만든 `src/dialect/postgres/systypes.zig`에서 옵니다. `pg_range`도 같은 곳에서 범위 타입 6개를 가집니다. 테이블과 뷰마다 행 타입과 그 배열(`_book`)이 있고, 시퀀스에는 없습니다(`reltype` 0).
- 시스템 열 `tableoid`: 테이블과 카탈로그 뷰의 `t.tableoid`(또는 FROM 항목이 하나일 때 `tableoid`)는 그 관계의 OID(`'schema.name'::regclass::oid`)입니다. psql의 `\dd`가 씁니다.
- `pg_available_extensions` 뷰와 FROM의 `pg_available_extensions()`(열 별칭 포함)는 `plpgsql` 하나를 보입니다. `pg_description`에 그 설명이 있어 `\dx`가 PostgreSQL과 같습니다.
- 키 열의 등호 조건(`pg_class.oid`, `pg_attribute.attrelid`, `pg_index.indexrelid`·`indrelid`, `pg_constraint.oid`·`conrelid`·`confrelid`, `pg_attrdef.oid`·`adrelid`, `pg_type.oid`, `pg_namespace.oid`, `pg_proc.oid`, `pg_sequence.seqrelid`, `pg_depend.objid`·`refobjid`, `pg_description.objoid`)은 가상 테이블이 그 OID의 행만 읽습니다. `attrelid = '16384'`, 조인의 `a.attrelid = c.oid`처럼 psql과 ORM이 쓰는 질의가 시스템 행(`pg_attribute`만 1100개 남짓)을 다 훑지 않습니다.
- `psql` 클라이언트의 메타 명령(`\dt`, `\di`, `\dv`, `\ds`, `\dn`, `\df`, `\d <table_name>`)이 네이티브 PostgreSQL 16/18과 완벽히 동일하게 동작합니다.
